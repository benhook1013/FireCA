## Important qualifications

**A small shared signer still serves many tenants and authorities.** Limiting the first custody topology does not remove multitenancy or require customer-specific pods. API and lifecycle workers can remain separately deployed and scale independently. Higher-scale signer allocation and automatic HA can follow a validated safety contract.

**Signer checks and independent approval are different guarantees.** Both proposals accept initial platform/operator trust. The signer must enforce tenant, issuer, key version, allowed operation and approved-input bindings. It cannot establish an independent authorization source by rereading records that a malicious trusted administrator controls. HSM integration changes some custody properties; it does not automatically change approval authority.

**Database locking is a candidate implementation mechanism, not a stop signal for a provider.** B suggests investigating serialization/locking for short software operations; A explicitly notes that connection loss does not stop an external provider. The prototype must preserve this distinction. Do not extend a lock-based software design to a slow HSM operation without revisiting interruption, execution and release semantics.

**A recovery epoch does not restore missing history or exclude an old signer.** A proposes a fresh epoch; both require process/provider exclusion and complete security-history reconciliation. A current local generation, new wrapping credential, deleted pod object or fresh issuer is insufficient on its own. Kubernetes documents that force deletion can permit a replacement while the old process remains alive, and PostgreSQL requires exclusion of the old primary after failover. Applying these facts to signing is a design inference that needs the proposed operating drill. [Kubernetes force deletion](https://kubernetes.io/docs/tasks/run-application/force-delete-stateful-set-pod/), [PostgreSQL failover](https://www.postgresql.org/docs/current/warm-standby-failover.html)

**A restored incomplete CRL must not be presented as complete current status.** Preserve available public artifacts subject to their actual freshness. If history cannot be recovered, the fallback requires demonstrated parent-revocation or relying-party distrust/blocking and replacement procedures; a new issuer alone does not invalidate the old certificates.

**DNS-01 does not require the application endpoint to be public.** It requires the validator to obtain the challenge TXT evidence in the supported DNS context. Public DNS challenge visibility and private endpoint reachability are separate choices; configured private DNS validation remains available to disconnected self-hosting. DNS challenges still need account, namespace and tenant authorization bindings. [RFC 8555 DNS challenge](https://www.rfc-editor.org/rfc/rfc8555.html#section-8.4)

**Native Windows success remains an experimental result to obtain.** A domain-local connector is a proposed way to isolate Windows authentication/directory integration. Microsoft documents native XCEP/WSTEP enrollment paths; that documentation does not prove a FireCA backend interoperates. Real unattended behavior and the intended use are separate acceptance evidence. [Microsoft native enrollment example](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cersod/e35f4aaa-9087-4513-845a-aabb7eb12418)

**Java remains the FireCA backend decision.** An external engine's implementation language alone does not determine FireCA's primary backend language. EJBCA is a reasonable Java comparison candidate; any alternative would need explicit operational and ownership evaluation rather than an implicit platform change.

**Browser keys, managed application keys, standalone keys and secrets remain in scope.** The proposed first synthetic slice uses CSR enrollment. It does not cancel the distinct custody flows or the eventual broader crypto product. Basic API, portal and ACME remain required for the first usable CA release; a CLI-only experiment does not meet that release gate.

## Proposed next work and ordering

1. **Record a short proposed decision packet.** Pilot hypothesis, trusted actors/privilege matrix, admission/suspension/release guarantees, wrapping/bootstrap/recovery ownership, ACME validation context, one observer, relying-client contract and commercial continuity. Select supported Java/library/build versions before runnable scaffolding.
2. **Run the bounded engine comparison and secure the Windows lab.** Use two synthetic tenant authorities, external-root signing, issuance/denial, revocation, rollover and recovery. Resolve ownership before freezing core issuance contracts. Do not require buyer interviews or every Windows scenario before reversible executable experiments.
3. **Build one narrow synthetic lifecycle slice and a separate Windows experiment.** API/ACME enrollment, a real observed TLS endpoint, tenant denial cases, revocation/client behavior, interrupted operations and issuer rollover. Windows evidence must come from patched real clients, with no mandatory PC agent.
4. **Demonstrate the operating model offline.** Initial install and independent administrator/TLS bootstrap; automatic or manual unlock as configured; wrapping rotation; fresh rebuild; old-signer exclusion; old-backup restore and quarantine/reconciliation. State the supported Kubernetes prerequisites and supplied offline artifacts.
5. **Revise the delivery gates using evidence, then assess the actual pilot.** Complete API/basic portal/ACME for the usable CA release. Require the pilot's necessary Windows, HSM or stronger-isolation evidence before that pilot, and establish its paid entitlement and continuity terms. Validate commercial value separately from engineering feasibility.

These are recommended next actions, not work implemented by this review. No outreach was performed. No prospective customer, Windows lab, engine result, provider guarantee, client revocation behavior or runtime version has been verified in this phase.
