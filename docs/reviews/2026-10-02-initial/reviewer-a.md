Reviewed `e5126db1271c80c810ae81ffec52b1a953eff7dd`. HEAD matched twice and the working tree was clean. I read AGENTS.md, README, LICENSE, all main design documents, all ADRs, and references. This is a documentation review; no application, interoperability, or security behavior was tested.

The direction is suitable for bounded feasibility work, but its current contracts and release gates are insufficient for a customer pilot. The objections below are ordered approximately by consequence. They challenge unresolved choices without replacing the accepted Java stack, paid organizational licensing, shared infrastructure, disconnected operation, or eventual native Windows enrollment.

1. **There is no demonstrated reason to build this breadth, or a decision about which CA responsibilities FireCA should own. — Before scaffolding substantive backend contracts.**

   A plausible failure is spending several milestones rebuilding issuance, ACME, custody, and administration, then discovering that prospective customers value an integration or operational outcome that still requires M6–M8.

   The scope addresses organizations, disconnected government environments, personal users, and integrations simultaneously ([product-scope.md:9](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/product-scope.md#L9)), while broadening from private CA and lifecycle management into keys and secrets ([product-scope.md:18](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/product-scope.md#L18)). Existing engines are merely evaluation candidates ([references.md:30](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/references.md#L30)); M0 requires tooling and module choices but no engine decision or customer evidence ([roadmap.md:11](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L11)).

   This is consequential because an existing engine could own issuance transactions, keys, profiles, revocation, and its own database. That changes FireCA’s contracts substantially. EJBCA documents multiple CAs in one installation and an enterprise native Windows enrollment offering; Smallstep already supplies ACME and HSM integrations, although its open-source CA has substantial limitations relevant here. These establish alternatives, not a recommendation to adopt either. [EJBCA architecture](https://docs.keyfactor.com/ejbca/9.3.2/ejbca-architecture), [EJBCA autoenrollment](https://docs.keyfactor.com/ejbca/latest/microsoft-auto-enrollment-overview), [Smallstep scope and limitations](https://smallstep.com/docs/step-ca/).

   **Resolve:** Choose the first paying use case and define its measurable benefit, migration path, assurance requirements, deployment cost, and willingness to pay. Compare a FireCA-owned CA core with a compatible Java engine using the same synthetic tenant/issuance/revocation workflow and actual edition/redistribution rights. Preserve the eventual scope, but gate expansion on a successful pilot. Commercial viability remains uncertain; the repository contains no customer validation.

2. **The signer’s independent security authority is undefined. — Before scaffolding role and authorization boundaries; enforcement before pilot.**

   Suppose the shared control plane is compromised and writes an “approved” request or changes tenant B’s profile in PostgreSQL. The signer could issue the attacker’s certificate while correctly enforcing structured inputs, permitted operation type, and ownership generation. Keeping private-key bytes outside HTTP responses does not prevent signing abuse.

   The control plane administers identity, authorization, and profiles; the signer consumes approved request bindings ([architecture.md:32](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L32)). Both use the authoritative database, which also holds permissions and audit metadata ([architecture.md:42](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L42)). The authorization contract requires carrying context, but does not identify who independently establishes the authenticity of that context ([domain-model.md:46](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/domain-model.md#L46)). Shared compromise is already acknowledged ([0001-platform-and-storage.md:22](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/decisions/0001-platform-and-storage.md#L22)).

   **Resolve:** State the supported threat model explicitly: are the control plane, database administrators, and platform operators trusted to authorize every tenant’s CA? That can be a valid initial boundary, but customers must understand it. If the signer is expected to withstand another role’s compromise, identify the independent approval/policy source and privileges that make this possible. Define controls for authority import, policy changes, exports, and recovery; decide how audit evidence survives the actors it is intended to audit. Prove cross-tenant denial through jobs and the signer, including forged context and altered approval records.

   An HSM later prevents certain key extraction; it does not automatically solve this authorization problem.

3. **PostgreSQL fencing is described within one history; disaster recovery can erase that history. — Design before distributed signing; demonstrate before pilot.**

   Consider issuing certificates and recording revocations after a backup, then restoring that backup while retaining the same CA key. The restored database can forget issued certificates, revocations, and ownership generations. An old signer or primary may still be alive. A locally increasing database counter cannot establish global monotonicity across those histories.

   Ownership generations and issuer/serial reservations are the safety basis ([architecture.md:52](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L52)); M2 recovery criteria preserve encryption metadata and provider references ([roadmap.md:35](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L35)). Broader failover verification appears in M8 ([roadmap.md:113](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L113)). PostgreSQL documents possible loss of committed transactions under asynchronous replication, and separately requires fencing the old primary after promotion. [PostgreSQL replication durability](https://www.postgresql.org/docs/current/warm-standby.html#SYNCHRONOUS-REPLICATION), [PostgreSQL failover](https://www.postgresql.org/docs/current/warm-standby-failover.html).

   **Resolve:** Specify the initial durability and recovery envelope: accepted issuance/revocation loss, failover policy, database and signer fencing, and how restored state is reconciled before signing resumes. Either prevent loss of security history or require a safe recovery procedure that recognizes it; random serial numbers alone would not recover forgotten revocations. Include tests for sign-success/result-persistence failure, suspension during an in-flight operation, primary promotion, and restore with an old signer still running. Define permitted interrupted-request outcomes without promising exactly-once HSM execution.

   This is required even for a low-throughput pilot. Sophisticated automatic HA can wait; safe manual recovery cannot.

4. **Software custody lacks an operational unlock and recovery model compatible with its customers. — Before implementing M2; before any custody pilot.**

   A cluster restart creates an unresolved tradeoff. Automatic unlock needs an accessible wrapping-key credential, potentially in the same administrative compromise domain as the signer. Human unlock can leave renewal and revocation unavailable until operators respond. Losing the recovery material can strand every issuer protected by it.

   The software provider must support wrapping, unlock, rotation, backup, restore, retirement, and deletion, but none is selected ([architecture.md:71](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L71)); durable encrypted storage is still open ([architecture.md:42](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L42)). HSMs and stronger isolation arrive only in M8 ([roadmap.md:105](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L105)). The documentation correctly rejects equivalence between tenant encryption keys and hardware isolation ([architecture.md:73](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L73)).

   **Resolve:** Choose who holds wrapping and recovery material, how initial provisioning and restart work, which administrators can recover keys, and how partially completed rotations are restored. Exercise restoration into a fresh environment, loss of one recovery component, and continued revocation for retired issuers. Establish that the first customers accept software custody. If a design partner requires a particular hardware or validated-module assurance level, move that provider experiment ahead of their pilot rather than treating M8 as universally late.

   I am not assuming that all government customers require an HSM. Their actual assurance requirements are unknown, which is the product risk.

5. **Hosted ACME for private names needs a validation topology that the architecture does not provide. — Before fixing gateway/connector contracts; verify before the M5 pilot.**

   A hosted customer requests `service.corp.example` whose HTTP endpoint and DNS challenge records are reachable only inside its network. The hosted validator cannot see them. Giving a shared validator unrestricted access through customer connectors creates an additional failure: tenant A causes requests into tenant B’s or the operator’s private network.

   Hosted and self-hosted deployments share the product ([product-scope.md:7](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/product-scope.md#L7)); private ACME is an initial-release commitment ([product-scope.md:28](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/product-scope.md#L28)). The gateway only maps into the control plane ([architecture.md:35](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L35)); tenant-local collectors are described for observations ([architecture.md:95](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L95)) and expand in M6 ([roadmap.md:83](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L83)).

   ACME validation involves server-originated network queries. Its security considerations explicitly discuss SSRF; public-Internet restrictions suggested for public validation cannot simply be imposed on FireCA’s private-PKI use case. External Account Binding can associate accounts, but does not itself authorize requested identifiers. [RFC 8555 protocol model](https://www.rfc-editor.org/rfc/rfc8555.html#section-5), [SSRF considerations](https://www.rfc-editor.org/rfc/rfc8555.html#section-10.4), [External Account Binding](https://www.rfc-editor.org/rfc/rfc8555.html#section-7.3.4).

   **Resolve:** Select supported challenges and identifier/network classes for the first hosted release. Decide whether it requires tenant-local validation, customer network connectivity, public DNS proof, or narrower advertised support. Bind resolver/connector selection and challenge results to tenant, authority, account, and request. Test private split DNS, overlapping customer names, redirects, rebinding, and cross-tenant routing. The existing “correct account mapping” acceptance criterion is insufficient.

6. **Independent trust domains and revocation require relying-party contracts before certificates escape into production. — Before pilot, with trust semantics fixed in the foundation.**

   Two tenants issue a client certificate for the same subject identity. A shared relying service trusts both roots and maps subjects to accounts without considering the issuer; tenant B’s certificate can impersonate tenant A. Separately, a pilot certificate contains a CRL URL tied to the first deployment hostname. After migration, rollover, or license expiry, that URL stops serving current status.

   The proposal asserts independent trust domains ([product-scope.md:46](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/product-scope.md#L46)), while trust-bundle distribution and revocation scope remain outstanding ([roadmap.md:125](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L125)). M3 demonstrates CRL behavior “where supported” ([roadmap.md:51](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L51)); fuller rollover and revocation freshness verification arrives at M8.

   X.509 validators operate on trust anchors and application policy, not FireCA tenant IDs. RFC 5280 also defines CRL freshness through `nextUpdate`; storing revocation is only one step. [Trust-anchor policy](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.2), [CRL next update](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.1.2.5).

   **Resolve:** Define supported trust provisioning, verifier identity mapping, and issuer constraints. Demonstrate rejection of the other tenant’s otherwise valid certificate using representative clients. Choose stable publication URLs, client checking behavior, freshness objectives, publication availability, and retention across issuer rollover. Test stale/unreachable revocation data and retire an issuer while its certificates remain in use. OCSP can wait where supported CRLs satisfy the pilot; publication continuity and explicit client behavior cannot.

7. **The Windows feasibility gate can be satisfied by native manual enrollment while the required unattended behavior remains unproved. — Before freezing identity/template contracts; full compatibility before a Windows pilot.**

   A successful `certreq` or MMC request proves a native client can obtain a certificate. It does not establish that machine and user autoenrollment run unattended after Group Policy changes, reboot, or renewal triggers. A team could pass the literal M1 criteria and discover much later that its authentication and template model cannot support the required automatic path.

   M1 asks for native policy discovery, enrollment, and renewal, and explicitly lacks a verified Windows/AD environment ([roadmap.md:21](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L21), [roadmap.md:25](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L25)). The connector topology remains undecided ([architecture.md:87](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L87)). Microsoft distinguishes authentication/bootstrap modes and documents Group Policy integration; native protocol support is only part of the deployment. [Microsoft autoenrollment model](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cersod/dd492d51-9c18-4d52-a8db-e9cfe35a80b2), [Microsoft enrollment authentication and topology](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/certificate-enrollment-web-service).

   **Resolve:** Obtain the real test environment first. Require unattended machine and user enrollment and renewal with no endpoint agent, plus permission removal, account disablement, directory-derived identities, and recovery from unavailable gateways. Record a supported version/domain/authentication matrix and explicit exclusions such as DCOM compatibility or key archival.

   If AD certificate-based authentication is an intended profile, also demonstrate strong certificate mapping on patched domain controllers; merely issuing a certificate with a UPN is insufficient. This is conditional, not an assertion that every Windows TLS certificate needs a SID extension. [Microsoft strong-mapping requirements](https://support.microsoft.com/en-us/servicing/os/windows-server/2022/05/kb5014754-certificate-based-authentication-changes-on-windows-domain-controllers).

8. **Disconnected commercial operation has no first-pilot continuity or maintenance contract. — Before organizational evaluation/pilot; packaging details can follow the selected deployment profile.**

   An offline customer’s license expires during procurement delays. Renewal stops, existing certificates subsequently expire, and critical services fail even though the license flag never changes certificate cryptographic validity. Another customer cannot patch or restore because the distributable installation assumes access to package registries or retained operator credentials.

   Local signed licenses and bundled assets are accepted ([architecture.md:101](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/architecture.md#L101)); expiry behavior is expressly undefined ([licensing.md:46](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/licensing.md#L46)). Evaluation and contributor rights are unfinished ([licensing.md:30](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/licensing.md#L30)). M5 tests absence of callbacks, while commercial self-hosting acceptance appears in M8 ([roadmap.md:76](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L76), [roadmap.md:115](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L115)).

   **Resolve:** Establish evaluation/deployment entitlement and a documented continuity policy before organizational pilots. Specify behavior for expiry, renewal, clock problems, license verification-key changes, emergency administration, revocation publication, recovery, and data export. Test installation, restart, upgrade, rollback, and restore with external networking denied and only the supplied artifacts. Choose one initial supported Kubernetes/self-hosting profile and its maintenance responsibilities. “No mandatory callback” is necessary but does not demonstrate operable disconnected deployment.

A further sequencing consequence runs through objections 1 and 5: lifecycle management should have a real deployment observation path in its pilot. M4 preserves “unknown” correctly, but collectors arrive in M6 ([roadmap.md:53](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L53), [roadmap.md:83](https://github.com/benhook1013/FireCA/blob/e5126db1271c80c810ae81ffec52b1a953eff7dd/docs/roadmap.md#L83)). A selected TLS endpoint observer could be enough initially. The pilot should prove that renewal reaches the intended deployment, or clearly sell issuance/inventory rather than a validated deployment-health outcome.

My assessment is **proceed with a minimal experimental scaffold, not yet with broad product implementation**. The minimum next decisions or experiments are:

- Choose the first paying use case and record the build-versus-engine result.
- Fix the signer/control-plane/operator trust model.
- Design recovery across database, keys, issuance history, and revocation history.
- Demonstrate unattended native Windows enrollment in the actual proposed topology.
- Demonstrate tenant-bound private ACME validation and one observed deployment lifecycle.
- Define first-pilot trust/revocation publication, disconnected maintenance, and commercial continuity.

Exact object names, build tooling, portal styling, additional collectors, general secrets, and broad HSM coverage can remain later choices. The boundaries above determine whether those later implementations can deliver the accepted product safely and commercially.
